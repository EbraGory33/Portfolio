## Why I Built This

Most developer portfolios are assembled as a collection of disconnected sections: an introduction, a list of technologies, a few project links, and a contact button.

I wanted this portfolio to feel like a product instead.

The goal was to create a cohesive interface where every part of my work could be explored through the same visual system. Projects needed to be more than thumbnails. My experience needed to be more than a résumé copied into a webpage. My GitHub activity needed to be current rather than manually maintained. Navigation needed to remain useful without taking attention away from the content.

That led to a portfolio built around reusable layouts, structured content, interactive visualizations, and small details that make the site feel responsive to the person using it.

The result is a portfolio that serves two purposes:

- It introduces who I am and how I work.
- It demonstrates the frontend architecture and interaction design I use to build products.

## Architecture Overview

The project is organized into four primary layers.

**Route layer** — Next.js App Router pages define the public routes for the homepage, about page, project catalog, individual project case studies, skills page, and GitHub API endpoint.

**Content layer** — Project case studies live as MDX files in the repository. Each file combines YAML frontmatter with long-form Markdown content. The frontmatter supplies titles, descriptions, dates, technology tags, links, highlights, and imagery.

**Component layer** — Reusable components handle layout, navigation, cards, project previews, MDX content, GitHub statistics, the footer, and page-specific sections. Pages are assembled from these primitives instead of duplicating markup.

**Data layer** — Local MDX files provide project content, local TypeScript data supplies navigation and experience information, and GitHub data is fetched from the REST and GraphQL APIs.

```filetree
src/
  app/
    page.tsx — Homepage route
    about/
      page.tsx — About and experience route
    projects/
      page.tsx — Project catalog
      [slug]/
        page.tsx — Dynamic MDX project route
    skills/
      page.tsx — Skills route
    api/
      github/
        route.ts — GitHub data endpoint
  content/
    projects/
      ebrahimgory.mdx — Portfolio case study
      travel-guide.mdx — Travel Guide case study
  components/
    cards/ — Bento cards and interactive overlays
    layout/ — Page, content, section, and grid primitives
    mdx/ — Code blocks, file trees, and content wrappers
    menu/ — Command-style navigation drawer
    pages/ — Homepage, about, project, and shared sections
    project/ — Project previews, metadata, and MDX presentation
    sections/
      github/ — GitHub profile, graph, statistics, and overlays
  lib/
    data/ — Navigation, experience, background, and GitHub data
    hooks/ — Menu, theme, and project hooks
    mdx/ — Project loading, parsing, compilation, and plugins
    providers/ — Shared React context providers
    types/ — Project, experience, file-tree, and technology types
```

This separation keeps route files small while allowing the component and content systems to evolve independently.

## File-Based Project Publishing

Each project starts as an MDX file.

The file begins with frontmatter describing the project:

```yaml
---
title: "Project Name"
description: "Long-form project description."
summary: "Short description for project previews"
published: "Q3 2026"
updated: "Q3 2026"

type: "Web Application"
role: "Frontend Developer"

tech:
  - NEXT.JS
  - REACT
  - TYPESCRIPT

github: "https://github.com/example/project"
live: "https://example.com"

featured: true

cover: "/images/project/cover.webp"
thumbnail: "/images/project/thumbnail.webp"
---
```

Below the frontmatter, standard Markdown becomes the body of the case study.

At runtime, the loader reads the project directory, filters for MDX files, derives each slug from its filename, and parses the frontmatter with `gray-matter`. The project catalog uses this metadata to generate preview cards.

When someone opens an individual project, the dynamic route loads the corresponding MDX file and compiles its body with `next-mdx-remote`.

This provides a simple publishing workflow:

1. Create an MDX file.
2. Add its frontmatter.
3. Write the case study.
4. Add the required images.
5. The project becomes available to the catalog and dynamic route.

There is no external CMS or separate content API. The content is versioned alongside the components that render it.

## Custom MDX Rendering

The project does not render MDX as unstyled HTML.

A custom component map replaces standard Markdown elements with components created specifically for the project detail layout:

- `h2` becomes a numbered project heading.
- Inline `code` uses a dedicated inline-code component.
- Fenced code blocks render through a reusable content-block system.
- Images use a project-specific image component.
- Horizontal rules become styled project dividers.
- Content is grouped into custom project sections.

The compiler also runs a small remark pipeline:

- `remark-gfm` adds GitHub-flavored Markdown behavior.
- A custom section plugin organizes the document into renderable project sections.
- A custom code-metadata plugin reads information attached to fenced code blocks.

For example, a code fence can include a file path:

```ts src/lib/mdx/loader.ts
export async function getProject(slug: string) {
  const filePath = path.join(
    process.cwd(),
    PROJECT_DIRECTORY,
    `${slug}${PROJECT_EXTENSION}`,
  );

  const source = await fs.readFile(filePath, "utf8");
  const { data, content } = parseMDX(source);
  const { content: compiled } = await compileProject(content);

  return {
    slug,
    frontmatter: parseFrontmatter(data),
    content: compiled,
  };
}
```

That metadata can then be presented as part of the code-block interface rather than being displayed as ordinary code.

This system lets case studies stay readable as Markdown while still matching the rest of the application.

## Responsive Bento Interface

The homepage is organized around a responsive bento grid.

Instead of treating each section as a full-width block, the interface combines focused cards that introduce different parts of the portfolio:

- My background and journey
- Technology stack
- Project outcomes
- Location and remote availability
- Development tools

Each card follows the same composition:

1. A reusable grid item controls its responsive position.
2. A shared card shell handles surface styling and overflow.
3. A visual overlay owns the interactive or decorative content.
4. A shared footer presents the title and supporting description.

The grid changes structure across breakpoints. Cards that occupy a single column on smaller screens can span multiple columns and rows on larger displays.

This allows the homepage to remain compact without turning into a rigid dashboard. Every card can have its own visual identity while still belonging to the same system.

## Interactive WebGL Globe

The location card uses `cobe` to render an interactive globe on a canvas.

The globe marks New York and adapts its palette to the active theme. Light and dark modes use different base, glow, map, and marker colors so the visualization feels native to both appearances.

Interaction is handled with pointer events:

- Pressing the canvas begins a drag.
- Horizontal movement rotates the globe.
- Vertical movement adjusts its angle.
- Releasing the pointer preserves momentum.
- Velocity gradually decays to create inertia.
- When movement settles, automatic rotation resumes.
- Vertical rotation is clamped to prevent disorienting angles.

The renderer also limits its device pixel ratio to avoid unnecessarily expensive canvas dimensions on very high-density displays.

```ts
const globe = createGlobe(canvas, {
  devicePixelRatio: Math.min(window.devicePixelRatio, 2),
  width: width * 2,
  height: width * 2,
  phi: 0,
  theta: DEFAULT_THETA,
  dark: isDark ? 1 : 0,
  mapSamples: 40000,
  markers: cities.map((city) => ({
    id: city.id,
    location: city.location,
    size: 0.025,
  })),
});
```

The component listens for window resizing and updates the renderer dimensions whenever the card changes size. On unmount, it cancels the animation frame, removes the listener, and destroys the globe instance.

The result is a small interactive detail that communicates location without relying on a static map screenshot.

## Live GitHub Data

The about page includes an open-source section built from live GitHub data.

Three requests run concurrently:

1. The GitHub REST API retrieves profile information.
2. The repositories endpoint retrieves public repositories.
3. The GitHub GraphQL API retrieves contribution-calendar data.

The repository response is reduced into aggregate star and fork counts. The profile response supplies follower information. The GraphQL response supplies total contributions and the contribution calendar used by the visual graph.

```ts
const [profileResponse, reposResponse, contributionsResponse] =
  await Promise.all([
    fetch(`https://api.github.com/users/${GITHUB_USERNAME}`, options),
    fetch(
      `https://api.github.com/users/${GITHUB_USERNAME}/repos?per_page=100`,
      options,
    ),
    fetch("https://api.github.com/graphql", graphQLOptions),
  ]);
```

Every request checks its response before attempting to render the data. When an API request fails, the thrown error includes the username, HTTP status, status text, and response body to make debugging easier.

The completed section presents:

- GitHub profile information
- Contribution totals
- Contribution calendar
- Follower count
- Combined repository fork count
- Combined repository star count

The requests use Next.js revalidation, allowing the portfolio to show recent activity without making a new GitHub request on every render.

## Scroll-Driven Experience Timeline

The experience section uses a vertical timeline to connect career entries visually.

A profile image moves down the timeline as the reader progresses through the section. The interaction is based on the section's actual scroll position rather than a fixed-duration animation.

Motion's `useScroll` tracks progress from the start of the experience container to its end. `useSpring` smooths the raw value, and `useTransform` converts the normalized progress into a vertical position.

```ts
const { scrollYProgress } = useScroll({
  target: containerRef,
  offset: ["start center", "end center"],
});

const progress = useSpring(scrollYProgress, {
  stiffness: 70,
  damping: 22,
  mass: 0.9,
});

const imagePosition = useTransform(progress, [0, 1], ["0%", "100%"]);
```

The same spring value scales the colored progress line from its top edge.

Because the animation is tied directly to the content container, it continues to work when experience entries change height or when the layout shifts between mobile and desktop breakpoints.

This turns a conventional career list into a visual narrative without hiding the underlying information.

## Command-Style Navigation

The site navigation is implemented as a bottom drawer with a command-style interface.

The menu groups navigation into two areas:

- Internal pages such as Home, About, Work, and Skills
- External profiles such as GitHub, LinkedIn, Instagram, and X

The current route is derived from the pathname and reflected visually in the corresponding menu item. Active links receive a distinct surface, icon treatment, ring, and animated status indicator.

The drawer also includes:

- A direct email action
- A light/dark theme toggle
- A close control
- Screen-reader-only title and description content
- External-link indicators
- Focus-visible styles for keyboard navigation

Menu state is kept in a small React context provider. This allows header controls and other descendants to open or close the drawer without coupling them directly to the menu implementation.

Search is visually represented in the command interface, but it is intentionally marked as under construction rather than presented as a completed feature.

## Theme System

The application supports light mode, dark mode, and the visitor's system preference through `next-themes`.

The theme provider is mounted in the root layout with `defaultTheme="system"` and `enableSystem`. Components can then read the resolved appearance when they need more than CSS-based dark-mode styling.

Most surfaces use Tailwind's dark variants, while interactive canvas content receives explicit theme-dependent values.

This is particularly important for the globe. A CSS class cannot recolor pixels already rendered into a WebGL canvas, so the globe component reads the resolved theme and rebuilds its renderer with the appropriate color configuration.

The interface therefore maintains the same hierarchy and contrast across both themes instead of treating dark mode as an inverted afterthought.

## Project Discovery

Project content is reused in multiple contexts.

The homepage loads all project frontmatter and passes the resulting collection to the featured-project section. The work page uses the same loader to build the complete project catalog. Individual project pages use the filename-derived slug to locate and compile the full case study.

This keeps project metadata consistent:

- Titles come from the MDX frontmatter.
- Preview descriptions come from the same source.
- Cover and thumbnail paths remain attached to the project.
- Technology labels are shared between previews and detail pages.
- Source and live links appear in the project metadata section.
- Featured projects can be identified without maintaining another list.

Technology names are restricted to a shared TypeScript registry. The same registry associates each supported technology with an icon, ensuring that project files and visual badges use a common vocabulary.

## Component Architecture

The interface is built from small, purpose-specific components.

Layout primitives define the structural vocabulary:

- `PageBuilder` controls page-level width and grid behavior.
- `Content` constrains the main content region.
- `SectionBuilder` standardizes section headers and spacing.
- `BentoGrid` and `BentoGridItem` define responsive card placement.
- `BackgroundImage` handles decorative page imagery.

Feature components then compose those primitives:

- Homepage sections assemble the hero, information cards, projects, and about content.
- Project components handle previews, links, metadata, technology tags, and MDX content.
- GitHub components separate profile information, contribution visualization, statistics, and overlays.
- Menu components handle navigation, social links, contact actions, and theme controls.

This approach prevents page routes from becoming large presentation files. The routes decide what data to load and which page component to render; the component system owns the interface.

## Responsive Design

Responsiveness is treated as part of the architecture rather than a final styling pass.

The bento grid changes its spans and row behavior across mobile, tablet, and desktop layouts. Project cards expose separate mobile and desktop presentations. The experience timeline changes its horizontal position depending on available space. Typography, spacing, and content padding scale across breakpoints.

The project pages also account for long content:

- The central project column uses `min-width: 0` to prevent overflow.
- Article content uses a full-width prose layout.
- Metadata shifts from one column to two columns on large screens.
- Technology badges occupy a dedicated panel on desktop.
- Decorative backgrounds remain separate from the readable content layer.

The aim is not simply to make the desktop design narrower. Each layout adapts its structure to the space available.

## Key Decisions

### MDX over hard-coded project pages

Every project needs both structured metadata and long-form storytelling.

A TypeScript object works well for a project card but becomes uncomfortable for an entire case study. A standalone page component provides flexibility but duplicates route and layout code for every project.

MDX sits between those approaches. Frontmatter gives the project catalog predictable metadata, while Markdown provides a practical writing format for the full case study. Custom components preserve the visual system where plain HTML would be too limited.

### Local content over an external CMS

This is a personal portfolio, so editorial collaboration is not a core requirement.

Keeping project content inside the repository provides:

- Git-based revision history
- No external content API
- No CMS authentication surface
- No synchronization between code and content
- The ability to update a component and its documentation together

The tradeoff is that publishing requires a code deployment. For a developer-owned portfolio, that is a reasonable constraint.

### REST and GraphQL together

GitHub's REST API is well suited to profile and repository information. Contribution calendars are better represented through GitHub's GraphQL schema.

Using both APIs avoids forcing every data requirement through a single interface. The application can request each dataset from the endpoint that represents it most naturally, then normalize the results into one view model for the UI.

### Context for shared menu state

The menu can be opened from outside the drawer component, so keeping its state inside the menu would make external controls difficult to coordinate.

A focused provider exposes only the operations the interface needs: whether the menu is expanded, how to toggle it, and how to close it. This is enough shared state for the feature without introducing a broader state-management dependency.

### Reusable primitives over page-specific markup

The same section spacing, page widths, card structures, metadata rows, and project treatments appear throughout the application.

Extracting these patterns into components keeps the layout consistent and makes later changes less error-prone. It also makes page files easier to understand because their structure reads as composition rather than implementation detail.

## Challenges

### Making MDX feel native to the interface

Rendering Markdown was straightforward. Making it look like a deliberate part of the portfolio required more work.

Headings needed numbering, code blocks needed metadata, images needed consistent framing, and document sections needed predictable spacing. The custom MDX component map and remark plugins became the bridge between an author-friendly file and a design-specific result.

### Coordinating canvas state with React state

The globe is managed by an imperative rendering library, while theme changes and component lifecycle are managed by React.

The component needed to create the renderer only after the client mounted, rebuild it when the resolved theme changed, update its dimensions when the window resized, and destroy it cleanly when the component unmounted.

It also needed to keep drag state, momentum, and rotation outside normal React rendering so pointer movement would not trigger a component render on every frame.

### Presenting remote data reliably

The GitHub section combines multiple API responses with different data shapes.

Running the requests concurrently improves latency, but each response still needs independent validation. The resulting REST and GraphQL payloads then have to be reduced into a stable structure that presentation components can consume without understanding the original APIs.

### Maintaining visual consistency across themes

Dark mode affects more than background and text colors. Transparent surfaces, borders, shadows, icons, images, and WebGL rendering all need coordinated values.

Using CSS variants for standard components and explicit configuration for the canvas renderer allowed both themes to share the same design hierarchy without forcing every feature into one styling mechanism.

## What I Learned

**Content architecture changes how quickly a portfolio can grow.** Once the MDX loader, dynamic route, and custom components were in place, adding a project became a writing task rather than a page-development task.

**Reusable components work best when they encode a real design decision.** Components such as the section builder, bento card, project metadata panel, and MDX heading are useful because they preserve consistent behavior, not merely because they reduce line count.

**Imperative graphics require disciplined cleanup.** Animation frames, event listeners, pointer capture, renderer instances, and canvas dimensions all exist outside React's declarative model. Managing their lifecycle explicitly is essential.

**Live data should be transformed before it reaches the UI.** The GitHub components do not need to understand separate REST and GraphQL payloads. A dedicated data function performs the requests and converts the responses into the shape the interface needs.

**Responsive design is easier when layout responsibilities are explicit.** Separating page containers, content regions, section builders, grid items, and feature components makes it clearer which layer should own each breakpoint decision.

**A portfolio can demonstrate engineering through its structure.** The case studies show the finished work, but the component system, publishing pipeline, data integration, interaction design, and responsive behavior demonstrate how that work is built.
